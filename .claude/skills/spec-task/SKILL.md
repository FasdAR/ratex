# Правила работы
- Не читай исходники проекта.
- Детальную сверку с кодом не делай. Всё, что требует чтения кода, записывай в «Проверить в коде».
- Если описания задачи нет, спроси его через `AskUserQuestion`.

# Данные на вход
- description - Равняется $ARGUMENTS, описание задачи пользователем. Может быть текстом или путём к файлу.

# Данные на выход
- Подробное ТЗ по [шаблону](references/result-template.md).

# Правила сбора ТЗ
- Не пересказывай и не переопределяй `CLAUDE.md`, `AGENTS.md` и общие правила проекта.
- Если дано готовое ТЗ, сохрани его существенные требования без упрощения.
- Выяви пробелы и противоречия в описании пользователя. Для поиска пробелов пройди по [списку типовых пробелов](references/gaps-checklist.md). Список — только источник вопросов, а не готовые требования.
- Каждый пункт помечай источником: `[пользователь]`, `[ответ на QA-n]` или `[предположение]`.
- Разделяй вопросы:
  - о продукте и поведении (что должно происходить, для кого, где границы) — задавай пользователю;
  - о текущей реализации (какой экран, есть ли кэш, как устроен API, где хранятся данные) — не задавай, записывай гипотезой в «Проверить в коде».

# Правила формирования вопросов
- Задавай вопросы только через `AskUserQuestion`. Его ограничения:
  - до 4 вопросов за вызов;
  - 2–4 варианта ответа на вопрос;
  - заголовок (`header`) не длиннее 12 символов;
  - вариант «Other» добавляется сам, не добавляй его.
- Спрашивай только то, что влияет на требуемое поведение, границы задачи или критерии приёмки.
- Сначала задавай блокирующие вопросы, потом остальные.
- Рекомендуемый вариант ставь первым и добавляй к его метке «(Рекомендуется)».
- Сам не выбирай ответ по умолчанию. Неотвеченный вопрос остаётся в «Открытых вопросах».
- Не больше 2 раундов вопросов. После ответов один раз проверь, не появились ли новые пробелы или противоречия; если появились — это и есть второй раунд.

# Правила формирования результата
- Заполняй [шаблон](references/result-template.md) целиком, порядок и названия разделов не меняй. Если в разделе нечего писать, укажи «Нет».
- Пункты нумеруй сквозь весь документ, номера не переиспользуй:
  - требуемое поведение — `RB-1`, `RB-2`…;
  - критерии приёмки — `AC-1`…;
  - допущения — `AS-1`…;
  - проверить в коде — `CC-1`…;
  - открытые вопросы — `QA-1`….
- Ссылайся на пункты по идентификаторам (например, `AC-2 проверяет RB-1`, `AS-1 снимается ответом на QA-3`).
- Критерии приёмки делай проверяемыми, в формате Дано / Когда / Тогда, и указывай, какие `RB` они покрывают.
- У каждого открытого вопроса укажи `[блокирует]` или `[не блокирует]` и что именно он блокирует.

# Алгоритм работы
1. Получи `description`. Если это путь — прочитай файл. Если описания нет — спроси его.
2. Сориентируйся в названиях, которые упомянул пользователь.
3. Собери черновик ТЗ по [правилам сбора ТЗ](#правила-сбора-тз).
4. Если есть вопросы к пользователю, задай их по [правилам](#правила-формирования-вопросов) и обнови черновик.
5. Сформируй результат по [правилам](#правила-формирования-результата) и [шаблону](references/result-template.md).
6. Верни результат своей работы в виде собранного ТЗ.
