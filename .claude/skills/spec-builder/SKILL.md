# Правила работы
- Не меняй код проекта и не пиши файлы.
- Этапы выполняй строго по скиллам `spec-task` и `spec-feasibility`. Если скилл ещё не загружен в контекст, вызови его через `Skill`.
- Вопросы пользователю задавай там, где этого требует скилл этапа, и по его правилам.

# Данные на вход
- description - Равняется $ARGUMENTS: описание задачи текстом или путём к файлу. Либо результат прошлой проверки `spec-feasibility` (текст или путь) — тогда это продолжение.

# Данные на выход
- Результат `spec-task` — собранное ТЗ.
- Результат `spec-feasibility` — проверка ТЗ по коду. Он дополняет ТЗ, поэтому читать их нужно вместе.

# Алгоритм работы
1. Если на входе результат прошлой проверки (есть разделы «Вердикт» и «Основа»), пропусти шаги 2–3 и выполни `spec-feasibility` с ним на входе.
2. Выполни `spec-task` с `description` на входе. Не переходи к следующему шагу, пока этап не завершён: вопросов к пользователю нет или исчерпаны 2 раунда.
3. Выполни `spec-feasibility` с результатом `spec-task` на входе: текст целиком, без изменений и сокращений. Ответы на вопросы этого этапа не меняют результат `spec-task`.
4. Верни результаты обоих этапов (при продолжении — только `spec-feasibility`).
