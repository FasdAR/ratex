# Правила работы
- Не меняй код проекта.
- Если ТЗ не передано, спроси его через `AskUserQuestion`.

# Данные на вход
- description - Равняется $ARGUMENTS, ТЗ по [шаблону входа](references/input-template.md). Может быть текстом или путём к файлу.

# Данные на выход
- Проверенное ТЗ с оценкой реализуемости по [шаблону результата](references/result-template.md).

# Правила проверки по коду
- Код подтверждает текущее поведение и технические ограничения. Желаемое поведение и разрешение противоречий в требованиях выбирает пользователь; не подменяй его ответ предположением о коде.
- Проверь каждый пункт `CC-n`: отметь `[подтверждено]`, `[опровергнуто]` или `[не удалось проверить]` и дай ссылку `путь:строка`.
- Каждый открытый вопрос `QA-n` попробуй закрыть по коду. Закрывай только вопросы о текущей реализации и только при наличии подтверждения со ссылкой `путь:строка`. Вопросы о продукте и поведении оставляй пользователю.
- Для каждого `RB-n` оцени реализуемость: `[реализуемо]`, `[реализуемо с доработкой]`, `[конфликт с кодом]` или `[неясно]` — с коротким обоснованием и ссылками.
- Допущения `AS-n` с источником `[предположение]` сверь с кодом; опровергнутые превращай в вопрос пользователю или в исправленное допущение с источником `[код: путь:строка]`.
- Опиши текущее поведение по коду со ссылками, не смешивая его с требуемым.
- Найди затрагиваемые модули, файлы и зависимости, технические ограничения и риски.
- Разбей реализацию на логические этапы в порядке выполнения. У каждого этапа укажи, какие `RB` и `AC` он закрывает и где меняется код. Каждый `RB` должен войти хотя бы в один этап. Если вердикт `Не реализуемо`, этапы не составляй.
- Не превращай догадки о коде в требования.

# Правила формирования вопросов
- Задавай вопросы только через `AskUserQuestion`. Его ограничения:
  - до 4 вопросов за вызов;
  - 2–4 варианта ответа на вопрос;
  - заголовок (`header`) не длиннее 12 символов;
  - вариант «Other» добавляется сам, не добавляй его.
- Спрашивай только то, что нельзя решить по коду и что влияет на требуемое поведение, границы задачи или критерии приёмки: противоречия ТЗ и кода, выбор между вариантами реализации с разным поведением, оставшиеся блокирующие `QA-n`.
- В вопросе коротко укажи, что найдено в коде (со ссылкой), чтобы пользователь понимал, почему его спрашивают.
- Сначала задавай блокирующие вопросы, потом остальные.
- Рекомендуемый вариант ставь первым и добавляй к его метке «(Рекомендуется)».
- Сам не выбирай ответ по умолчанию. Неотвеченный вопрос остаётся в «Открытых вопросах».
- Не больше 2 раундов вопросов. После ответов один раз проверь, не появились ли новые противоречия; если появились — это и есть второй раунд.

# Правила формирования результата
- Заполняй [шаблон результата](references/result-template.md) целиком, порядок и названия разделов не меняй. Если в разделе нечего писать, укажи «Нет».
- Сохраняй идентификаторы из входного ТЗ (`RB`, `AC`, `AS`, `CC`, `QA`). Новые пункты продолжают нумерацию; номера не переиспользуй, удалённые пункты не перенумеровывай.
- Закрытый вопрос переноси в «Закрытые вопросы» с ответом и источником: `[пользователь]` или `[код: путь:строка]`.
- Существенные требования входного ТЗ сохраняй без упрощения. Если требование изменилось после ответа пользователя, укажи `[изменено: ответ на QA-n]`.
- Вердикт:
  - `Готово` — нет блокирующих открытых вопросов и конфликтов с кодом;
  - `Нужны ответы` — остались блокирующие вопросы;
  - `Не реализуемо` — требование противоречит ограничению, которое нельзя снять в рамках задачи (укажи какому).

# Алгоритм работы
1. Получи `description`. Если это путь — прочитай файл. Если ТЗ нет — спроси его.
2. Проверь ТЗ по коду по [правилам проверки](#правила-проверки-по-коду).
3. Если остались вопросы к пользователю, задай их по [правилам](#правила-формирования-вопросов) и обнови ТЗ.
4. Сформируй результат по [правилам](#правила-формирования-результата).
5. Верни результат своей работы в виде проверенного ТЗ.
