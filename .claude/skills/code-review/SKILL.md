# Правила работы
- Не меняй код проекта и не пиши файлы.
- Не запускай сборку, компиляцию, тесты и lint. Не делай коммит и push.
- Если `spec` не передано, проверяй только корректность и правила проекта и скажи об этом в результате.

# Данные на вход
- spec: String? — ТЗ задачи с критериями приёмки. Текст или путь к файлу.
- previous: String? — замечания прошлого раунда ревью. Текст или путь к файлу. Если задан — проверь, исправлены ли они.

Значения берутся из $ARGUMENTS: именованные `spec: …` и `previous: …`; один безымянный аргумент — это `spec`.

# Данные на выход
- ReviewResult по [шаблону результата](references/result-template.md): `status` (`Успех` или `Есть замечания`), что проверено, замечания, статус замечаний прошлого раунда.

# Правила сбора изменений
- Работай в корне Git-репозитория (`git rev-parse --show-toplevel`).
- Собери полный набор незакоммиченных файлов:
  - staged — `git diff --cached`;
  - unstaged — `git diff`;
  - новые — `git ls-files --others --exclude-standard`.
- Учитывай удаления и переименования. `git diff` без `--cached` недостаточен: он не показывает staged и новые файлы.
- Если изменений нет, верни статус `Успех` с пометкой «Нет изменений».

# Правила проверки
- Прочитай `CLAUDE.md`, изменённые файлы и необходимый соседний код. Ищи через `ast-index` (`class`, `usages`, `implementations`, `callers`); Grep — только если `ast-index` ничего не нашёл. Файл длиннее 200 строк сначала смотри через `ast-index outline`, затем читай нужный фрагмент через `offset`/`limit`.
- Проверь:
  - корректность и реальные сценарии использования, крайние случаи;
  - соответствие `spec`: каждый `RB-n` и `AC-n` реализован, нет лишнего вне рамок задачи;
  - правила проекта из `CLAUDE.md`: слои `ui → domain ← data` и направление зависимостей, общее в `core`, DI (provision-методы `AppComponent`, ветка в `CurrencyViewModelFactory`), корутины (`suspend`, `withContext(ioDispatcher)`, rethrow `CancellationException`, `viewModelScope`), один `StateFlow` на ViewModel, ошибка как поле состояния;
  - стиль ktlint по `.editorconfig` (без запуска) и тесты рядом с изменённым кодом, если их требует `spec`.
- Отделяй доказанные дефекты от предположений. В замечания попадают только доказанные; предположения не включай. Замечаний только ради стиля не делай.
- Для каждого пункта `previous` определи: `[исправлено]` или `[не исправлено]` со ссылкой `путь:строка`.

# Правила формирования результата
- Заполняй [шаблон результата](references/result-template.md) целиком, порядок и названия разделов не меняй. Если в разделе нечего писать, укажи «Нет».
- Каждое замечание нумеруй `RV-1`, `RV-2`… и указывай:
  - важность: `критично` | `важно` | `мелочь`;
  - точное место: `путь:строка`;
  - сценарий ошибки;
  - ожидаемое поведение;
  - конкретное исправление.
- Замечания упорядочивай по важности.
- Статус:
  - `Успех` — нет подтверждённых замечаний и все пункты `previous` исправлены;
  - `Есть замечания` — есть хотя бы одно подтверждённое замечание или неисправленный пункт `previous`.

# Алгоритм работы
1. Получи `spec` и `previous`. Если это пути — прочитай файлы.
2. Собери изменения по [правилам сбора](#правила-сбора-изменений).
3. Проверь их по [правилам проверки](#правила-проверки).
4. Сформируй результат по [правилам](#правила-формирования-результата).
5. Верни результат своей работы.
