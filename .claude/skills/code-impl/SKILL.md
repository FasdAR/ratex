# Правила работы
- Правь только файлы проекта, которых требует ТЗ.
- Не запускай сборку, компиляцию, тесты и lint. Не создавай и не меняй тесты, если ТЗ этого не требует. Не делай commit и push.
- Сохраняй чужие незакоммиченные изменения: не откатывай и не переписывай то, что не относится к ТЗ.
- Не придумывай требования. Если для выбора существенного поведения данных не хватает — спроси через `AskUserQuestion`.
- Если `spec` не передано, спроси его через `AskUserQuestion`.

# Данные на вход
- spec: String — ТЗ задачи с критериями приёмки. Текст или путь к файлу. Ровно то, что реализуется.
- remarks: String? — замечания к уже сделанной реализации или диагностика упавших проверок. Текст или путь к файлу. Если задан — это исправление, а не новая реализация.

Значения берутся из $ARGUMENTS: именованные `spec: …` и `remarks: …`; один безымянный аргумент — это `spec`.

# Данные на выход
- ImplResult по [шаблону результата](references/result-template.md): `status`, изменённые файлы, соответствие критериям приёмки, непроверенные риски, вопросы.

# Правила реализации
- Перед правкой прочитай `CLAUDE.md` и текущий код вокруг места изменения. Ищи через `ast-index` (`class`, `usages`, `implementations`, `callers`); Grep — только если `ast-index` ничего не нашёл. Файл длиннее 200 строк сначала смотри через `ast-index outline`, затем читай нужный фрагмент через `offset`/`limit`.
- Выполняй пункты ТЗ по порядку. Каждый `RB-n` и `AC-n` должен быть реализован или явно объявлен нереализованным с причиной.
- Меняй минимум файлов и держи локальный стиль: именование, плотность комментариев, ktlint-правила (`.editorconfig`, строка до 140 символов).
- Соблюдай архитектуру проекта из `CLAUDE.md` там, где она относится к задаче: слои `ui → domain ← data`, общее — в `core`, DI через provision-методы, `suspend` + `withContext(ioDispatcher)`, ошибки через `try/catch` с rethrow `CancellationException`, состояние ViewModel одним `StateFlow`.
- Если `remarks` задан, исправляй только подтверждённые им дефекты и не расширяй объём правок. Неверное замечание не игнорируй молча: верни доказательство из кода (`путь:строка`) в «Отклонённые замечания».
- После правок проверь результат чтением изменённых файлов и `git diff`.

# Правила формирования вопросов
- Задавай вопросы только через `AskUserQuestion`. Его ограничения:
  - до 4 вопросов за вызов;
  - 2–4 варианта ответа на вопрос;
  - заголовок (`header`) не длиннее 12 символов;
  - вариант «Other» добавляется сам, не добавляй его.
- Спрашивай только то, что нельзя решить по ТЗ и коду и что меняет поведение.
- Рекомендуемый вариант ставь первым и добавляй к его метке «(Рекомендуется)».
- Сам не выбирай ответ по умолчанию. Если ответа нет, не реализуй зависящую от него часть и верни её в «Вопросы».
- Не больше 2 раундов вопросов.

# Правила формирования результата
- Заполняй [шаблон результата](references/result-template.md) целиком, порядок и названия разделов не меняй. Если в разделе нечего писать, укажи «Нет».
- Статус:
  - `Готово` — все `RB` и `AC` реализованы;
  - `Нужны ответы` — часть ТЗ не реализована из-за вопросов без ответа;
  - `Ошибка` — реализацию довести нельзя (противоречие ТЗ и кода, которое не снять вопросом).
- В «Соответствие критериям приёмки» перечисли каждый `AC-n` с отметкой и ссылкой `путь:строка`.
- Явно укажи, что сборка и тесты не запускались.

# Алгоритм работы
1. Получи `spec` и `remarks`. Если это пути — прочитай файлы. Если `spec` нет — спроси его.
2. Изучи код и состояние Git по [правилам реализации](#правила-реализации).
3. Реализуй ТЗ или исправь `remarks`. Если нужны ответы, задай их по [правилам](#правила-формирования-вопросов).
4. Проверь результат чтением и `git diff`.
5. Сформируй результат по [правилам](#правила-формирования-результата).
6. Верни результат своей работы.
